## Architecture and HTTPS

- **MongoDB Atlas** hosts the production database. Create a database user with a unique strong password and grant only the database permissions the app needs. Store the Atlas connection string in Render as `MONGODB_URI`, never in the repository. Add the Render service's current outbound IP addresses to the Atlas IP access list; do not leave a broad `0.0.0.0/0` rule in place.
- **Render** runs the Express API from `server/`. The Blueprint is `render.yaml`; its health check is `/api/health`. Render's managed TLS terminates HTTPS for the API. The Blueprint uses a paid web-service plan with a persistent disk mounted at `/var/data`, and stores uploaded files under `/var/data/uploads`.
- **Vercel** serves the Vite/React client from `client/`. Its `vercel.json` sets the build output, SPA fallback and security headers. Vercel provides HTTPS for the deployment URL.
- In Vercel, set `VITE_API_URL` to the Render API URL with `/api` appended for Production. In Render, set `CORS_ORIGIN` to the exact Vercel production frontend origin (scheme and hostname only, no path). For local development, use `http://localhost:5173` as the allowed origin. Preview deployments can call the API only when their exact stable origin is also allow-listed by Render; do not use wildcard CORS to accommodate temporary preview URLs.

## One-time setup

1. Create a MongoDB Atlas cluster and database user. Configure network access for the Render service's outbound IPs, then copy the application's database connection string.
2. Connect the repository to Render using the root `render.yaml` Blueprint. Confirm the service deploys from `main`. Set `MONGODB_URI` and `CORS_ORIGIN` in the Render dashboard. `JWT_SECRET` is generated by the Blueprint; keep it private and do not rotate it without planning for existing sessions to become invalid.
3. Create a Vercel project connected to this repository, set its project root to `client`, and set the production branch to `main`. Add `VITE_API_URL=https://<render-service>.onrender.com/api` for Production and Preview as appropriate.
4. Confirm both platforms are configured to deploy production only from `main`. Use the Render and Vercel health/deployment dashboards to verify the first deploy; check `https://<render-service>.onrender.com/api/health` returns `{"status":"ok"}`.
5. Replace the TBD URLs above and add the verified frontend/API links to the project README after checking the live application over HTTPS.

## Automatic deployment flow

1. A push to any branch runs GitHub Actions CI. Pull requests targeting `main` also run CI, including both test suites, coverage collection/upload, and the frontend production build.
2. Merge a reviewed PR into `main` only after required checks pass. Vercel creates a production deployment from the configured production branch. Render's Blueprint uses `autoDeployTrigger: checksPass` and deploys the backend from `main` after GitHub checks pass.
3. Vercel embeds `VITE_API_URL` at build time. If the backend URL or CORS allow-list changes, update the corresponding platform environment variable and redeploy/rebuild the affected service.
4. Verify the frontend loads over HTTPS, the API health endpoint is healthy, login works, and the browser console/network panel shows no CORS errors.

## Rollback

- **Render API:** open the service's Events/Deploys page, select the last known-good deploy and choose **Rollback**. Confirm `/api/health` and login after rollback. Keep `MONGODB_URI`, `JWT_SECRET`, and `CORS_ORIGIN` unchanged unless the incident specifically requires updating them.
- **Vercel frontend:** open the project's Deployments, select the last known-good Production deployment and use **Promote to Production** (or redeploy that deployment). Verify the live URL and API connectivity.
- **Database:** do not roll back by pointing production at a test/local database. Use the Atlas backup/restore workflow for data incidents; coordinate the restore window because writes made after the backup may be lost.
- For a code regression, revert the offending merged PR through a new reviewed PR to `main`; CI and the hosting platforms will deploy the revert. Avoid force-pushing shared branches.

## Operational limitations and follow-up

- The Blueprint uses a paid Render web-service plan because persistent disks are not available for free services. The disk preserves study-material uploads across deploys, but only one service instance can mount it and deployments can have brief downtime. Back up important uploads separately; a persistent disk is not a substitute for backups.
- The API's in-memory login lockout counter is per process and is reset by a process restart. Keep the service at one instance; if it is scaled or requires durable lockout state, move the counter to shared storage (for example Redis) or enforce it at a shared edge/API gateway.
